# 고졸 문과생에게 설명할 수 있는 Mini Redis 학습 자료

## 1. 이 과제를 한 문장으로 설명하면

“이름표를 주면 물건을 빨리 찾아주고, 자리가 부족하면 오래 안 쓴 물건을 치우며, 유통기한이 지나면 버리는 작은 보관소를 만든다”입니다.

프로그램에서는 이름표를 **키(key)**, 보관할 내용을 **값(value)**이라고 부릅니다. `name`이라는 키에 `Alice`라는 값을 넣으면, 나중에 `name`만 말해도 `Alice`를 찾습니다.

```text
SET name Alice
GET name
```

첫 명령은 저장이므로 `OK`, 둘째 명령은 조회이므로 `"Alice"`가 나옵니다. 이 작은 경험이 전체 과제의 출발점입니다.

이 자료는 수학 공식을 외우는 대신, 물건을 어떻게 배치해야 찾기 쉬운지 이해하는 데서 시작합니다. 이후 실제 코드가 그 일을 어떻게 하는지 연결합니다.

## 2. 프로그램을 배우기 전에 알아둘 말

**프로그램**은 컴퓨터에게 시킬 일을 순서대로 적은 것입니다. **코드**는 그 지시를 Python 같은 언어로 작성한 글입니다.

**변수**는 값에 붙인 이름입니다. `used_memory = 12`는 “현재 사용량이라는 이름으로 12를 기억해라”라는 뜻입니다. 여기서 `=`는 수학의 등호와 달리 저장하라는 뜻이고, 같은지 비교할 때는 `==`를 씁니다.

**함수**는 여러 지시를 하나의 이름으로 묶은 것입니다. **인자**는 함수에 건네는 재료이고, **반환값**은 함수가 돌려주는 결과입니다. `get("name")`은 `get`에게 `name`을 찾아 달라고 부탁하는 모양입니다.

**클래스**는 비슷한 물건을 만드는 설계도입니다. **객체**는 그 설계도로 만든 실제 물건입니다. `Entry` 설계도로 키 하나에 관한 정보를 담는 객체를 만듭니다. 객체 안에 붙은 함수는 **메서드**라고 부릅니다. `self`는 “지금 이 객체 자신”을 뜻합니다.

**조건문**의 `if`는 “만약 ~라면”이고, **반복문**의 `for`와 `while`은 같은 일을 여러 번 하라는 뜻입니다. `return`은 결과를 돌려주고 함수를 마칩니다. `None`은 값이나 연결 대상이 없다는 표시입니다.

**자료구조**는 자료를 담고 연결하는 방식입니다. 정리함, 번호표, 대기 줄처럼 목적에 따라 다르게 배치합니다. **알고리즘**은 그 자료를 가지고 문제를 해결하는 절차입니다.

**CLI**는 글자로 명령을 입력하는 화면입니다. **REPL**은 입력(Read) → 실행(Evaluate) → 출력(Print) → 반복(Loop)입니다. 파일 이름이 `.py`로 끝나면 Python 코드이고, `.md`는 지금 읽는 것과 같은 문서입니다.

## 3. 우선 직접 실행하기

프로젝트 폴더에서 터미널을 열고 아래 명령을 실행합니다.

```powershell
python -m mini_redis
```

`python`은 실행 도구, `-m mini_redis`는 이 폴더의 `mini_redis` 프로그램을 실행하라는 뜻입니다. 도구를 찾지 못하면 [README](../README.md)의 실행 안내를 확인하세요.

`mini-redis>`가 나타난 뒤 아래를 한 줄씩 입력합니다.

```text
SET student "김 철수"
GET student
EXISTS student
DBSIZE
DEL student
GET student
quit
```

차례대로 `OK`, `"김 철수"`, `(integer) 1`, `(integer) 1`, `(integer) 1`, `(nil)`이 나옵니다. 마지막 `quit`은 종료합니다.

`integer`는 정수라는 뜻이고, `(nil)`은 찾는 값이 없다는 뜻입니다. `(nil)`과 빈 문자열 `""`은 다릅니다. 빈 종이가 보관되어 있는 것과 보관물이 없는 것은 다르기 때문입니다.

## 4. 왜 단순한 목록으로 찾지 않을까?

학생 카드 1만 장을 한 줄로 세워 두었다고 생각해 봅시다. 특정 이름을 찾으려면 맨 앞부터 하나씩 확인할 수 있습니다. 찾는 이름이 마지막에 있으면 1만 장을 봐야 합니다.

이처럼 자료가 늘어날수록 확인 횟수가 비례해서 늘어나는 것을 **O(n)**이라고 씁니다. 여기서 `n`은 자료 개수입니다. “오 엔”이라고 읽으면 됩니다.

반대로 번호표가 알려주는 칸으로 바로 가는 일처럼, 자료가 늘어도 단계가 대체로 일정한 작업을 **O(1)**이라고 부릅니다. “정확히 1초”나 “딱 한 번 실행”이라는 뜻은 아닙니다. 자료 개수에 따른 작업량 증가를 설명하는 표현입니다.

**O(log n)**은 여러 단계로 범위를 줄이거나 트리의 층을 따라가는 작업입니다. 크기가 2배가 될 때 단계는 대략 하나 늘어납니다. 8, 16, 32개의 자료를 다룰 때 필요한 층수는 대략 3, 4, 5단계 수준입니다.

실제 시간에는 키 길이, 컴퓨터 성능, 확장 작업도 영향을 줍니다. 평균 O(1)이라는 말만 보고 모든 상황에서 같은 시간이 걸린다고 설명하면 안 됩니다.

## 5. 해시맵: 이름표를 칸 번호로 바꾸기

읽을 코드: [hash_map.py](../mini_redis/hash_map.py)

정리함에 8개의 칸이 있다고 합시다. 이름표를 보고 매번 같은 칸 번호를 계산할 수 있다면 그 칸만 확인하면 됩니다. 이 계산 규칙을 **해시 함수**, 각 칸을 **버킷**이라고 합니다.

프로그램의 문자열은 컴퓨터가 다루는 작은 숫자인 바이트로 바꿀 수 있습니다. 이 코드에서는 UTF-8 규칙으로 바꾼 각 바이트를 읽으며 다음을 반복합니다.

```python
result = (result * 31 + byte) & 0xFFFFFFFFFFFFFFFF
```

이 문장을 처음부터 외울 필요는 없습니다. “이전 계산값을 31배 하고 새 숫자를 더한다”가 중심입니다. 마지막 부분은 숫자가 끝없이 커지지 않도록 아래쪽 64비트만 남기는 장치입니다. 이 상수는 보안 암호가 아닙니다.

예를 들어 영문 `A`의 바이트 값은 65입니다. `A`의 계산값은 65이고, 8로 나눈 나머지는 1이므로 1번 칸에 갑니다. `%`가 나머지를 구하는 기호입니다. 배열의 칸 번호는 0부터 시작하므로 8칸의 번호는 0~7입니다.

서로 다른 이름이 같은 칸으로 갈 수 있습니다. 이를 **충돌**이라고 합니다. 충돌은 저장 오류가 아닙니다. 같은 아파트 동에 여러 집이 있듯이, 그 칸 안에서 실제 이름표를 다시 비교하면 됩니다.

이 구현은 같은 칸에 속한 자료를 연결 리스트로 잇습니다. 이 방법이 **체이닝**입니다. `put`은 실제 키가 같으면 값을 바꾸고, 같은 칸이지만 다른 키라면 새 자료를 연결합니다.

칸이 너무 붐비면 찾기가 느려집니다. **로드 팩터**는 `자료 개수 / 버킷 개수`입니다. 8칸에 6개면 0.75이고, 7개면 0.875입니다. 0.75를 **초과**할 때 16칸으로 확장합니다. 칸 수가 바뀌면 나머지 계산도 달라지므로 기존 자료도 다시 배치합니다.

평균적으로 한 칸에 자료가 적으면 찾기가 빠릅니다. 하지만 충돌이 몰리면 여러 개를 읽어야 하므로 최악에는 O(n)이 될 수 있습니다. 이 구현은 악의적인 충돌을 방어하는 보안용 해시맵은 아닙니다.

설명 연습: “해시맵은 이름을 계산해서 칸을 고릅니다. 같은 칸에 여러 이름이 들어오면 실제 이름을 비교합니다. 너무 붐비면 칸을 늘립니다.”

## 6. 이중 연결 리스트: 앞뒤 사람을 기억하는 줄

읽을 코드: [linked_list.py](../mini_redis/linked_list.py)

사람마다 자기 앞사람과 뒷사람을 기억하며 줄을 섰다고 생각해 봅시다. 이때 각 사람 역할을 하는 작은 묶음이 **노드**입니다.

- `data`: 노드가 담는 내용.
- `prev`: 바로 앞 노드.
- `next`: 바로 뒤 노드.

맨 앞을 `head`, 맨 뒤를 `tail`이라고 부릅니다. 앞 또는 뒤에 아무도 없으면 연결값은 `None`입니다.

```text
head → A ↔ B ↔ C ← tail
```

B를 빼려면 A의 뒷사람을 C로, C의 앞사람을 A로 바꿉니다. 나머지 모든 사람을 한 칸씩 옮길 필요가 없습니다.

```text
head → A ↔ C ← tail
```

B를 맨 앞으로 옮길 때도 B를 떼고 앞에 연결하면 됩니다. `move_to_front`는 같은 B 노드를 다시 사용합니다. 노드를 새로 찾는 과정이 없으므로 연결을 바꾸는 단계는 O(1)입니다.

중요한 조건이 있습니다. **B의 위치를 이미 알고 있어야 합니다.** “이름이 B인 사람을 맨 앞부터 찾아라”는 검색을 먼저 하면 그 검색은 O(n)일 수 있습니다. 다음 장에서 해시맵이 이 위치를 알려줍니다.

`owner`는 노드가 어느 리스트에 속했는지 확인하는 보조 정보입니다. 다른 줄의 사람을 실수로 빼거나 이미 뺀 노드를 또 빼는 오류를 막습니다.

## 7. LRU: 가장 오래 사용하지 않은 물건부터 치우기

읽을 코드: [store.py](../mini_redis/store.py)의 `get`, `set`, `_evict`

**LRU**는 Least Recently Used의 줄임말이며 “가장 오래 사용하지 않은 것”입니다. 처음 넣은 순서와는 다릅니다. 오래전에 넣었어도 방금 꺼내 봤다면 최근 사용한 것입니다.

이 저장소의 연결 리스트는 왼쪽이 최근 사용, 오른쪽이 오래 사용하지 않은 키입니다.

```text
SET a 1    → a
SET b 2    → b ↔ a
SET c 3    → c ↔ b ↔ a
GET a      → a ↔ c ↔ b
```

이때 공간이 부족하면 맨 뒤의 `b`부터 제거합니다.

해시맵은 키로 `Entry`를 찾아주고, `Entry.lru_node`는 그 키의 줄 위치를 바로 알려줍니다. 그래서 해시맵 조회 후 노드를 앞에 옮길 수 있습니다. 해시맵 조회는 평균 O(1), 연결 변경은 O(1)입니다.

성공한 `SET`, `GET`만 사용 순서를 갱신합니다. `EXISTS`는 실제 값을 꺼내지 않는 확인 명령이므로 이 구현에서는 순서를 바꾸지 않습니다. `TTL`, `EXPIRE`, `KEYS`, `DBSIZE`, `INFO`도 마찬가지입니다.

LRU 추적 자체가 빠르다고 SET 전체가 항상 O(1)은 아닙니다. 한 번에 여러 키를 제거하거나 TTL 힙에서 삭제하는 일까지 생기면 추가 시간이 필요합니다.

## 8. 바이트와 메모리: 글자 수와 저장 크기는 다르다

**바이트**는 저장 크기를 세는 단위입니다. 이번 과제는 UTF-8로 표현했을 때 키와 값이 차지하는 바이트만 셉니다.

```text
엔트리 크기 = 키의 UTF-8 바이트 수 + 값의 UTF-8 바이트 수
전체 사용량 = 저장된 모든 엔트리 크기의 합
```

`user:1`은 6바이트, `Alice`는 5바이트이므로 합계는 11바이트입니다. `user:2`와 `Bob`은 9바이트, `user:3`과 `Charlie`는 13바이트입니다.

세 항목을 모두 넣으면 `11 + 9 + 13 = 33`입니다. 한도가 30이고 중간에 조회가 없었다면 가장 오래된 `user:1`을 제거합니다. 남은 양은 `33 - 11 = 22`입니다.

한글 `이름`은 UTF-8로 6바이트, `철수`도 6바이트이므로 `SET 이름 철수`는 12바이트입니다. 이 예의 한글 음절 한 글자는 3바이트입니다. 모든 문자가 항상 3바이트인 것은 아닙니다.

덮어쓰기는 새 크기를 그냥 더하면 안 됩니다. 기존 크기를 빼고 새 크기를 더합니다. 삭제·만료·LRU 제거도 같은 기준으로 사용량을 줄입니다.

한도가 5인데 키와 값 하나의 합이 6이면 다른 것을 다 버려도 저장할 수 없습니다. 이때 OOM, 즉 메모리 부족 오류를 냅니다. 이 구현은 먼저 크기를 검사하므로 유효한 기존 값을 덮어쓰려다 실패해도 원래 값은 남습니다.

`used_memory`는 과제의 계산용 숫자입니다. 연결 노드나 버킷 공간을 제외하므로 작업 관리자에 표시되는 Python의 실제 메모리 사용량과 다릅니다. `maxmemory 0`은 공간 0이 아니라 한도 없음을 뜻합니다.

## 9. TTL: 유통기한 붙이기

**TTL**은 Time To Live이며 “남아 있는 유효 시간”입니다. `EXPIRE name 3`은 지금부터 3초 뒤 만료되도록 설정합니다. `TTL name`은 얼마나 남았는지 묻습니다.

```text
현재 시각이 100초일 때 EXPIRE name 3
만료 시각은 103초
현재 시각이 101.2초면 남은 시간은 1.8초
TTL 출력은 내림하여 (integer) 1
```

남은 0.8초는 `(integer) 0`입니다. 0이 나왔다는 이유만으로 이미 지워졌다고 판단하면 안 됩니다. 정확히 만료 시각에 도달하면 삭제되고, TTL은 -2가 됩니다.

- `-2`: 키가 없습니다. 만료되어 지워진 경우도 포함합니다.
- `-1`: 키는 있지만 시간 제한이 없습니다.
- `0 이상`: 남은 초의 소수점 아래를 버린 값입니다.

`SET`으로 값을 덮어쓰면 기존 유통기한을 지웁니다. TTL을 연장하거나 단축하려면 `EXPIRE`를 다시 사용합니다. 0 또는 음수 초는 즉시 삭제입니다.

이 프로그램의 시계는 달력의 날짜 대신 경과 시간 측정용 `time.monotonic()`입니다. 저장소가 실행 중인 동안 흐른 시간을 비교하려는 목적입니다.

## 10. 최소 힙: 가장 급한 유통기한을 맨 위에

읽을 코드: [min_heap.py](../mini_redis/min_heap.py)

유통기한을 매번 전부 훑으면 키가 많을수록 비쌉니다. 가장 빨리 만료되는 항목만 먼저 볼 수 있다면 편리합니다. **최소 힙**은 가장 작은 값을 맨 위에 놓는 자료구조입니다.

여기서 작다는 것은 만료 시각이 이르다는 뜻입니다. 원소는 `(만료 시각, 키)`의 짝입니다. 괄호로 묶은 이런 짝을 Python에서는 튜플이라고 합니다. 시각이 같으면 키를 비교해 순서를 정합니다.

힙은 부모가 자식보다 작거나 같도록 유지합니다. 모든 항목이 완전히 정렬된 것은 아닙니다. 맨 위가 최소라는 점을 보장합니다.

```text
        103
       /   \
     108   105
    /   \
  120   110
```

이 구조는 왼쪽부터 빈칸 없이 채우는 **완전 이진 트리**로 생각할 수 있습니다. 각 항목은 자식을 최대 둘 갖습니다. 위 그림을 배열에 `[103, 108, 105, 120, 110]` 순서로 저장할 수 있습니다.

0부터 세는 위치가 `i`라면 왼쪽 자식은 `2*i+1`, 오른쪽은 `2*i+2`, 부모는 `(i-1)//2`입니다. `//`는 나눈 결과의 소수점 아래를 버립니다. 예를 들어 위치 1의 두 자식은 위치 3과 4입니다.

새 원소는 배열 끝에 붙이고 부모보다 작으면 자리를 바꾸며 올라갑니다. 이것이 `_heapify_up`입니다. 맨 위를 꺼내면 마지막 원소로 빈자리를 채우고 작은 자식과 바꾸며 내려갑니다. 이것이 `_heapify_down`입니다. 비교·교환은 대략 트리 높이만큼 합니다.

이 구현은 TTL 취소를 위해 키의 배열 위치도 기억합니다. 그 위치 기록 역시 직접 만든 해시맵입니다. 두 원소를 교환하는 `_swap`은 위치 기록도 함께 바꿉니다. 그래야 나중에 엉뚱한 원소를 지우지 않습니다.

중간 원소를 지우면 마지막 원소로 빈칸을 채웁니다. 부모보다 작아졌으면 올라가고, 그렇지 않으면 내려가며 규칙을 회복합니다. 같은 키에 EXPIRE를 여러 번 호출해도 원소가 쌓이지 않습니다.

해시맵 조회를 평균 O(1)로 볼 때 힙 추가·삭제는 보통 O(log n), 최소값 확인은 O(1)입니다. 배열이나 해시맵을 확장하는 순간에는 별도 복사 비용이 발생합니다.

## 11. 세 자료구조가 같이 움직이는 순간

읽을 코드: [store.py](../mini_redis/store.py)의 `_delete`, `_purge_expired`

하나의 키는 값 저장소, 최근 사용 순서, 만료 일정에 걸쳐 등장합니다. 지울 때 한 곳만 지우면 다른 곳에 흔적이 남아 오류를 만듭니다.

그래서 `_delete`를 공통 삭제 절차로 만들었습니다.

1. 해시맵에서 엔트리를 제거합니다.
2. 해당 엔트리의 LRU 노드를 줄에서 뺍니다.
3. 힙에서 해당 키의 만료 일정을 지웁니다.
4. 엔트리의 바이트 크기만큼 사용량을 뺍니다.

직접 `DEL`을 했든, 유통기한이 지났든, 공간이 부족해 버리든 이 절차를 사용합니다. 메모리 부족 때문에 버린 경우에만 별도로 `evicted_keys`를 1 올립니다.

`GET`은 먼저 `_purge_expired`를 호출합니다. 힙 맨 위가 이미 만료되었으면 삭제하고, 다음 맨 위도 확인합니다. 아직 만료되지 않은 항목을 만나면 멈춥니다. 그 뒤 요청한 키를 조회합니다. 이미 만료되어 삭제된 키는 LRU 앞으로 옮기지 않습니다.

입력 대기 중에도 시계는 흐르지만 프로그램이 뒤에서 계속 삭제 작업을 하지는 않습니다. 다음 저장소 명령이 시작할 때 정리합니다. 따라서 사용자에게는 만료된 값을 보여주지 않으면서 별도 실행 흐름을 만들지 않아도 됩니다.

## 12. 동적 배열: 사물함이 부족하면 큰 사물함으로 옮기기

읽을 코드: [dynamic_array.py](../mini_redis/dynamic_array.py)

`[None] * 4`는 빈칸 4개를 만드는 표현입니다. 이 프로젝트에서 내장 list는 이런 고정 길이 저장 공간으로 사용합니다. 저장소를 Python의 dict로 대신하지 않습니다.

배열에 실제 들어 있는 개수가 `size`, 마련된 전체 칸 수가 `capacity`입니다. 4칸이 모두 찬 상태에서 하나를 더 넣으면 8칸짜리를 만들고 기존 4개를 복사합니다. 다음에는 16칸, 32칸으로 늘어납니다.

대부분의 추가는 빈칸에 하나 넣으면 끝나지만, 확장하는 한 번은 여러 원소를 복사합니다. 긴 추가 작업 전체를 나누어 보면 원소당 평균 비용이 일정한 것을 **분할 상환 O(1)**이라고 합니다.

중간에서 삭제하면 뒤의 원소를 당겨야 하므로 O(n)입니다. 힙은 마지막 원소를 삭제하는 방식을 사용하므로 이 밀어 당기기 비용을 피합니다.

## 13. 실제 코드 읽는 순서

처음부터 모든 줄을 이해할 필요는 없습니다. 한 번 읽을 때 한 가지 질문만 해결하세요.

1. `__main__.py`: 실행하면 어떤 함수로 가는가? → `main()`.
2. `cli.py`의 `main`: 입력과 출력은 어떻게 반복되는가?
3. `CommandProcessor.execute`: 명령 이름과 인자 개수는 어디서 검사하는가?
4. `store.py`의 `set`, `get`: 실제 저장과 조회는 어디서 하는가?
5. `Entry`: 키 하나가 어떤 정보를 같이 기억하는가?
6. `linked_list.py`: 줄에서 한 노드를 어떻게 빼는가?
7. `hash_map.py`: 칸 번호와 충돌은 어떻게 처리하는가?
8. `dynamic_array.py`, `min_heap.py`: 만료가 빠른 원소는 어떻게 위로 올라가는가?
9. 다시 `store.py`: 만료·LRU·메모리 사용량이 어떻게 하나로 연결되는가?
10. `tests/`: 이 행동이 맞는지 어떤 예로 확인했는가?

예를 들어 `GET a`를 따라가면 `main → execute → _run → store.get → _purge_expired → data.get → lru.move_to_front`의 흐름입니다. 키가 없으면 마지막 이동은 생략합니다. 함수 이름을 찾아가는 것만으로도 프로그램의 큰 흐름을 이해할 수 있습니다.

## 14. 자동 테스트는 왜 필요한가?

겉으로 GET이 맞아 보여도 내부 사용량이 틀릴 수 있습니다. 삭제된 키가 힙에 남거나, 연결 리스트의 앞뒤가 어긋날 수도 있습니다. 테스트는 이런 약속을 반복해서 확인하는 안전장치입니다.

```powershell
python -m unittest discover -s tests -v
```

`test_ttl_boundaries`는 만료 직전과 정확한 만료 시점을 확인합니다. 실제로 3초씩 기다리는 대신 `FakeClock`의 숫자를 바꿉니다. 시계가 100에서 103으로 이동했다고 프로그램에 알려 주는 방식입니다. 테스트가 빠르고 재현 가능해집니다.

무작위 테스트는 여러 종류의 연산을 섞은 뒤 “키 개수와 LRU 노드 수가 같은가?”, “엔트리 크기의 합이 사용량과 같은가?”, “TTL 있는 키와 힙 원소가 일치하는가?”를 확인합니다. 이렇게 항상 유지되어야 할 규칙을 **불변식**이라고 합니다.

모든 테스트가 통과했다는 것은 검사한 조건에서 맞았다는 뜻입니다. 모든 가능한 입력이나 실제 Redis와의 완전한 호환성을 증명하는 것은 아닙니다.

## 15. 다른 사람에게 설명하는 5분 발표 순서

먼저 `SET name Alice`와 `GET name`을 실행하고 “이름표로 내용을 찾는 보관소”라고 소개합니다.

다음으로 “해시맵은 이름표를 칸 번호로 바꾼다. 충돌하면 같은 칸 안에서 실제 이름표를 비교한다”라고 설명합니다. 8개의 칸을 종이에 그려도 좋습니다.

그다음 카드 a, b, c를 놓고 `GET a`를 했을 때 a를 앞으로 옮깁니다. “공간이 부족하면 맨 뒤부터 지우는 LRU이고, 해시맵이 카드 위치를 알려줘서 빨리 옮긴다”고 설명합니다.

마지막으로 카드에 유통기한을 쓰고 “힙은 가장 빠른 기한을 위에 올려둔다. 만료된 카드는 값·순서·기한에서 모두 지우고 사용량도 뺀다”고 마무리합니다.

상대가 “왜 빠른가요?”라고 물으면 “모든 카드를 처음부터 찾는 작업을 줄이도록, 이름 검색·최근 순서·만료 순서에 각각 맞는 구조를 썼기 때문입니다”라고 답할 수 있어야 합니다.
