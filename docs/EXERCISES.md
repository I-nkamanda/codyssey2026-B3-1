# 직접 해보는 실습과 해설

각 실습은 `quit`으로 종료한 뒤 `python -m mini_redis`로 다시 시작하세요. 이전 실습의 데이터와 메모리 한도가 다음 실습에 영향을 주는 것을 막기 위해서입니다. 코드 블록에는 실제 명령어만 적었습니다.

## 실습 1. 키가 없을 때와 빈 값일 때

다음 GET 두 번은 같은 결과일까요?

```text
GET memo
SET memo ""
GET memo
DBSIZE
```

**해설:** 차례로 `(nil)`, `OK`, `""`, `(integer) 1`입니다. 빈 값도 저장된 값입니다. 내용이 없는 종이를 보관해 둔 것과 아무것도 없는 것은 다릅니다.

## 실습 2. 처음 넣은 순서와 최근 사용한 순서

마지막에 없는 키는 무엇일까요?

```text
CONFIG SET maxmemory 6
SET a 1
SET b 2
SET c 3
GET a
SET d 4
GET b
INFO memory
```

**해설:** 각 엔트리는 2바이트입니다. a, b, c까지 넣으면 6바이트입니다. GET a로 최근 사용 순서는 `a → c → b`가 됩니다. d를 넣으면 8바이트이므로 맨 뒤 b가 제거됩니다. GET b는 `(nil)`입니다. INFO는 사용량 6, 한도 6, 제거 횟수 1입니다.

추가 문제: `GET a`를 `EXISTS a`로 바꾸면 무엇이 지워질까요? **정답:** EXISTS는 LRU를 바꾸지 않으므로 a입니다.

## 실습 3. 한글의 메모리 계산

INFO의 사용량을 먼저 종이에 적어 보세요.

```text
SET 이름 철수
INFO memory
SET 이름 A
INFO memory
DEL 이름
INFO memory
```

**해설:** 사용량은 12 → 7 → 0입니다. `이름` 6바이트, `철수` 6바이트, `A` 1바이트입니다. 덮어쓰기는 12에 7을 더하는 것이 아니라 기존 12를 빼고 새 7을 더합니다.

## 실습 4. 실패한 덮어쓰기

두 번째 SET이 실패한 뒤 a의 값은 무엇일까요?

```text
CONFIG SET maxmemory 4
SET a 1
SET a 12345
GET a
INFO memory
```

**해설:** 새 엔트리는 1+5=6바이트라서 OOM입니다. 기존 값 `"1"`은 보존됩니다. 사용량 2, 한도 4, 제거 횟수 0입니다. `_delete`보다 OOM 검사를 먼저 하는 이유입니다.

## 실습 5. TTL과 덮어쓰기

```text
SET a first
EXPIRE a 30
TTL a
SET a second
TTL a
```

**해설:** 첫 TTL은 입력하는 데 걸린 시간에 따라 달라집니다. 만료 전에 실행하면 0~29가 보통이고, 같은 시각을 주입한 테스트에서는 30도 가능합니다. 30초 이상 지났다면 -2입니다. 두 번째 SET 직후 TTL은 -1입니다. 새 값으로 바꾸면 이전 만료 시간을 초기화하기 때문입니다.

## 실습 6. 정확히 만료되는 순간

```text
SET ticket valid
EXPIRE ticket 2
```

3초 정도 기다린 뒤 다음을 입력합니다.

```text
GET ticket
TTL ticket
DBSIZE
INFO memory
```

**해설:** GET은 `(nil)`, TTL은 -2, DBSIZE는 0입니다. 사용량도 0이며 evicted_keys는 0입니다. 시간이 지나서 삭제한 것은 메모리 한도 때문에 제거한 것과 구분합니다.

## 실습 7. 잘못된 입력에도 계속 동작하기

```text
HELLO
GET
CONFIG SET maxmemory abc
SET a "끝나지 않은 따옴표
SET a 정상
GET a
```

**해설:** 앞의 네 명령은 각각 알 수 없는 명령, 인자 개수, 정수, 따옴표 오류를 냅니다. 이후 SET은 `OK`, GET은 `"정상"`입니다. 사용자 입력 실수 때문에 프로그램 전체가 종료되면 안 됩니다.

## 실습 8. 해시 충돌을 손으로 계산하기

이 해시 함수는 문자열 바이트마다 이전 값에 31을 곱하고 새 바이트를 더합니다. 영문 A=65, a=97, B=66일 때 `Aa`와 `BB`의 계산값을 구해 보세요.

**해설:** `65×31+97=2112`, `66×31+66=2112`로 같습니다. 같은 버킷이어도 키 자체를 비교하면 둘을 구분할 수 있습니다. `test_collision_update_delete`는 한 키를 삭제한 뒤 다른 키가 남는지도 확인합니다.

## 실습 9. 힙 배열 해석하기

힙 배열이 `[2, 5, 3, 9, 8]`이라고 합시다. 루트, 위치 1의 부모, 위치 1의 두 자식은 무엇인가요? 배열 전체가 정렬되어 있나요?

**해설:** 루트는 값 2입니다. 위치 1의 부모는 위치 0의 값 2입니다. 자식은 위치 3의 값 9와 위치 4의 값 8입니다. 5 다음에 3이 나오므로 배열 전체는 정렬되어 있지 않습니다. 각 부모가 자식보다 작거나 같다는 규칙은 만족합니다.

## 실습 10. 삭제 경로 코드 읽기

`store.py`에서 `_delete`를 찾아 다음 질문에 답하세요.

1. 키가 없으면 무엇을 반환하나요?
2. 어떤 세 자료구조에서 제거하나요?
3. 사용량에서 무엇을 빼나요?
4. 이 함수 안에서 evicted_keys를 늘리나요?

**해설:** 1은 `False`, 2는 데이터 해시맵·LRU 리스트·TTL 힙, 3은 `entry.byte_size`입니다. 4는 아니며, 메모리 한도 제거를 담당하는 `_evict`에서만 증가시킵니다.

## 설명 능력 확인 질문

답을 가리고 1분씩 말해 보세요.

- 왜 해시맵은 충돌이 있어도 저장할 수 있나요? → 같은 버킷 안에서 실제 키를 비교하기 때문입니다.
- 연결 리스트만 있으면 LRU 이동이 항상 빠른가요? → 이동할 노드를 찾는 일이 필요합니다. 해시맵과 Entry의 노드 참조가 위치를 바로 알려줍니다.
- 힙이 TTL에 적합한 이유는 무엇인가요? → 가장 빠른 만료 시각을 맨 위에서 바로 확인할 수 있고, 추가·삭제 때 전체 정렬이 필요하지 않습니다.
- 메모리 사용량이 틀어지지 않게 하려면? → 모든 삭제 경로에서 같은 크기 계산과 공통 삭제 절차를 사용합니다.
- 실제 Redis 전체를 만든 것인가요? → 이 과제의 문자열·LRU·TTL을 갖춘 단일 CLI 프로그램입니다. 네트워크·영속성 등은 포함하지 않습니다.
